# B1: versionierte WebUI-Auslieferung

Basis: `base-commit` (`6ea12c1548d54095b1fe6f63f799bca61708ef44`). `b1.patch` enthält ausschließlich `api/auth.py` und `server.py`; `files/` enthält die zwei neuen Dateien. Die Live-Dateien wurden nur gelesen. Die bestehende Sicherung `/data/hermes/backups/b1-before-20261119T120703/` bleibt unangetastet.

Beim Add-on-Start prüft `apply.py` den exakten Git-Diff sowie beide neuen Dateien. Vollständiges B1 ist idempotent; andere oder teilweise Änderungen führen zum Abbruch der **WebUI**, nicht des Gateways. Auf einem sauberen Checkout wird B1 erst nach `git apply --check` angebracht. Bei aktivem Auto-Update und einem bereits mit B1 geänderten Checkout wird das Update ohne `reset`/`clean` übersprungen. Bei sauberem Checkout wird in `/data/hermes/webui-app.b1-stage` kopiert, dort `fetch`, `checkout`, Patch und Nachprüfung ausgeführt. Erst dann wird das alte Checkout in `/data/hermes/webui-app.b1-previous` umbenannt und das Stage an seine Stelle gesetzt. Ein vorhandenes Stage oder Previous blockiert weitere Staging-Updates; niemals automatisch löschen. Bei Upstream-Ausfall wird der vorhandene saubere Checkout gepatcht. Bei inkompatiblem Patch startet die WebUI nicht, Nginx liefert hierfür 502, Gateway und andere Ingress-Routen bleiben aktiv. Keine Migration der WebUI-Zustandsdateien; `/data/hermes/webui/ha-person-map.json` ist separat.

**Rollback, nur nach Freigabe und mit gestopptem Add-on:** Vorher Backup und Git-Status beider Checkouts sichern. Wenn `webui-app.b1-previous` existiert, aktuelles `webui-app` an einen neuen Sicherungspfad umbenennen und `webui-app.b1-previous` zurückbenennen; nicht löschen. Sonst die vier Originaldateien anhand des bestehenden B1-Backup-Manifests zurückspielen und nur die B1-Neudateien entfernen. Für eine vollständige Rückkehr zum alten Startverhalten müssen auch die Add-on-Image-Dateien (`run.sh`, `nginx.conf`, `Dockerfile`) aus einem vorherigen Stand wiederhergestellt werden; andernfalls verweigert der neue Starter zu Recht den Start einer ungepatchten WebUI. Die Personenzuordnung nicht blind löschen. Neustart/Reload nur mit gesonderter Freigabe.

Isolierte Tests (vom Repository-Stamm): `python3 -m unittest discover -s hermes_assistant/tests -p test_b1_delivery.py -v`; die sieben Tests kopieren das *tatsächlich installierte* WebUI-Checkout (in CI ein frisches Checkout desselben Commits), verändern es nicht. Abgedeckt sind sauberer und bereits vorbereiteter Checkout, Wiederholung, kompatibles Upstream-Staging, inkompatibles Upstream-Staging, fremde Änderungen und variable Git-Hash-Abkürzungen. Separat auf einer isolierten WebUI-Kopie: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_ha_person_assignment.py -v` im kopierten WebUI-Verzeichnis. Syntax: `bash -n hermes_assistant/run.sh`, `nginx -t -c "$PWD/hermes_assistant/nginx.conf"`, `python3 -m py_compile hermes_assistant/b1/apply.py`, `git diff --check`. Der Build-Healthcheck erwartet nun HTTP 403 von der absichtlich nur für HA-Ingress geöffneten Nginx-Route `/health`; er belegt Nginx-Erreichbarkeit, **nicht** WebUI- oder Gateway-Gesundheit. Das reale Verhalten dieses Healthchecks nach Add-on-Start ist noch nicht getestet. Ein echter Ingress-Aufruf mit zwei HA-Konten ist noch nicht geprüft. B1 ist Personalisierung, **keine** Trennung der FRIDAY-Gesprächslisten.
